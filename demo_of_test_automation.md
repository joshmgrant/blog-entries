This year, I had the pleasure of attending [Targeting Quality 2025](https://kwsqa.org/tq2025/schedule/) organized by the lovely people of [KWSQA](https://kwsqa.org/). This is a great conference for software quality professionals to meet and discuss aspects of software testing and quality, and have a nice chat or two.

One thing this year's conference got me thinking about was the rise of test automation frameworks for browser-based testing. These are frameworks like Cypress and Playwright, which many teams have chosen over using Selenium WebDriver-based test automation tools. It's almost expected that teams will pick one of these more recent tools than something using Selenium WebDriver.

A while ago (several years), there was some discussion in the test automation space that there wasn't really much "innovation" in test automation tools, or that there should be "more" innovation happening. I've thought about this notion for a while now, and gone back and forth on whether I agree with it or not. I think I'm coming down on the side that says yes, in fact, there has been significant innovation in the test automation world over the past 20 years or so. Mainly this has come from the democratization of test tools. 

Let me explain.

Once upon a time, tools that could test an application end-to-end -- opening the application in the actual environment an end user will see and exercising the app like an end user -- were expensive and proprietary. These tools were only really available to larger companies with big budgets and good reason to automate testing at scale. Examples would be SilkTest, IBM Rational Robot, and HP Quality Center. These tools were a heavy lift, needing dedicated installation and configuration both to integrate with the applications under test and with the testing teams eventually using the products. I'll also repeat that these tools were expensive, from both monetary and computational perspectives. These tools also existed before the web was full of applications that people use, and hence targeted platform-specific applications such as Windows-based desktop apps. The idea of a small-to-medium sized company investing in these tools for test automation was simply out of the question, let alone for a scrappy start-up. End-to-end test automation was only for large, well-established and relatively deep-pocketed organizations.

Then came Selenium.

Selenium was created as a free open source project and software. Being freely available meant anyone could use it, and -- crucially -- could use it at any scale without any configuration or licensing constraints. Eventually the Selenium project grew to include a suite of software tools for various needs of browser-based automation. The WebDriver could drive a browser, clicking buttons and refreshing pages and so on. The Selenium Grid provided ways to scale up running browsers on various machines and environments with different configurations for use with WebDriver. The client-server architecture of these tools meant that test suites for browser-based automation could happen at various scales, from a single browser running on a developer's machine to several autonomous environments running several browser instances and being controlled from a central hub. The rise of Selenium also occurred along with the rise of web applications. 

Put differently, Selenium democratized end-to-end test automation for the web. Not just big and deep-pocked companies could automate user testing; almost any web-savvy organization could do this as well. The success of the Selenium project also likely contributed to the creation of Appium, an open source tool that allows automating native mobile UI interfaces.

As time passed, there became more and more interest in test automation, particularly for smaller companies and organizations. Selenium was (and is!) a great tool for browser test automation, but the Selenium Webdriver itself is not a test framework. The WebDriver required working with an existing test framework, and does require additional configuration to get tests working effectively. The next stage of innovation was to create "ready-to-go" end-to-end test automation tools. These tools would be frameworks that provided everything needed to write tests, browser driving and all. 

The free open source aspect was validated as something that works and teams liked, so tools like Cypress and Playwright appeared. These tools were not just easy to get started with, but you could have a working test running in minutes. Instead of having one or more dedicated test automation specialists, now any reasonably competent developer could have browser-based end-to-end tests running within minutes. These tools were also CI-ready, as they coincided with the popularity of server-side JavaScript (hello NodeJS) and cloud-based computing. The democratization of test automation allowed even more development teams to write browser-based tests. Now even the scrappiest of startups or smallest of business units could have some kind of user acceptance testing.

What does this evolution mean for the future of the Selenium Project, the company behind Cypress, or the popularity of Playwright? I have absolutely no idea. These are all tools that have a proper context, and as long as they're available and working, people will use them. I do think that looking at these tooling developments through the lense of being more available for more software teams is helpful. The innovation that occurred in the software testing space was less making specific tooling better and more making general tooling and approaches more available to more people. This is a Good Thing.

Overall, more people getting into writing good test automation is a good thing for software development. Freedom to the people, or at least to SDETs.
